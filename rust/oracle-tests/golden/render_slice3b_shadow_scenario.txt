# === WHAT THIS PROVES: the two-pass shadow block paints real shadow pixels ===========
# `render_shadow` flips settings->shadow=true for the DRAW window only (AFTER the tick's
# sim Process ran, so it never reaches CorrectShadow — the sim stays byte-identical; the
# state_hash column is unchanged with vs without the flip). With the flip on, the FIRST
# pass (viewport.cpp:274-398) composites, for every visible worm, BlitShadowImage of the
# worm silhouette shifted (-3,+3): each silhouette pixel over terrain whose material sets
# kSeeShadow (material.hpp:11, 1<<4) is repainted with ShadowedArgb = pal32[idx+4]
# (shadow_query.hpp:51-68). Without a kSeeShadow material under the silhouette the pass
# runs but paints NOTHING (ShadowedArgb==0) — so the proof needs kSeeShadow terrain.
#
# === WHY see_shadow_test.lev (spec O3 empirical requirement) =========================
# physics_fall_test.lev's two materials (sky mat 8, dirt mat 1) carry NO kSeeShadow, so a
# shadow cast on it is invisible. The openliero TC's ONLY kSeeShadow material is value 24
# (kSeeShadow | kBackground) at palette indices 160..163 (tc.cfg `materials`). see_shadow_
# test.lev (gen_see_shadow_level.py) fills rows [0,340) with that material — a background
# the worm falls through but onto which its shadow DOES paint — over a solid floor at 340.
# Both worms sit in the band (y≈70), so their silhouettes fall entirely on kSeeShadow and
# the shadow pass paints on EVERY dumped tick.
#
# === THE EMPIRICAL DIFF (verified in the T7 report, spec O3 done-when) ===============
# Generating this SAME scenario WITH vs WITHOUT the `render_shadow` line yields DIFFERENT
# frame hashes on ticks 1..6 (11985d72… with shadow vs 14b1c310… without) while the
# state_hash column is byte-IDENTICAL (isolation intact). The differing pixels ARE the
# shadow pixels, and they live in the hashed back buffer → provably in the window. If the
# two runs were identical the shadow pass painted nothing → the golden would NOT be
# committed (spec O3). They differ → committed.
#
